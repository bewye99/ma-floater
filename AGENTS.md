# Repository Instructions

## Implementations and release boundary

- `main` contains the public PowerShell implementation and the in-progress .NET/WPF replacement. The PowerShell authoritative source is `src\MAFloater.ps1`; `bin\MAFloater.ps1` is generated by `Build.ps1`.
- The native replacement is under `src\MAFloater.App` and `src\MAFloater.Core`, with checks under `tests\MAFloater.FoundationChecks`. Its presence on `main` does not make it the default release.
- Keep the PowerShell implementation working as the reference until the native replacement is explicitly approved for release. A native change does not authorize replacing the launcher, scheduled task, or public release files.
- Preserve the existing architecture and make the smallest coherent change for the approved checkpoint. Do not mix unrelated legacy and native cleanup.

## Build and verification

- After changing the PowerShell application, run `Build.ps1` to regenerate `bin\MAFloater.ps1`, then run `Test.ps1`.
- After changing native C#, XAML, project, or native build files, run `Build-Native.ps1`. It restores, builds, runs the dependency-free foundation checks, and publishes the self-contained Windows x64 application.
- After changing installer files, run `Build-Installer.ps1` and `Test.ps1`. Installer compilation does not prove that a release is signed or allowed by Smart App Control.
- `Test.ps1` does not validate native behavior. `Build-Native.ps1` does not replace the PowerShell publication checks.
- For README or other public-documentation changes, run `Test.ps1`; an application build is unnecessary unless executable examples or build behavior changed.
- Review the final diff and working-tree status. Report what passed, failed, or remains unverified.

## Generated files and local state

- Do not hand-edit `bin\MAFloater.ps1`; regenerate it with `Build.ps1`.
- `artifacts\win-x64`, `artifacts\installer`, and each native project's `bin\` and `obj\` directories are untracked generated output. Do not commit them. The committed root `bin\MAFloater.ps1` is the legacy exception and must stay synchronized through `Build.ps1`.
- Settings and the DPAPI-protected Guest credential live under `%LOCALAPPDATA%\MAFloater`. Never print, copy into the repository, or commit credentials, tokens, or local settings.
- Preserve an existing MA Floater process, scheduled task, settings, and credential store unless the approved checkpoint explicitly includes changing them.

## Music Assistant safety boundaries

- Maintain the dedicated Music Assistant **Guest** account requirement. Do not broaden the account role or player permissions as a workaround.
- Keep Music Assistant authorization scoped to API requests. Artwork must use the separate unauthenticated client and retain its download-size limit.
- Automated tests must verify the exact queue or player targeted by each control command.
- Live validation must not start playback. If a queue is already playing and the approved checkpoint includes control validation, limit it to the specifically approved action and restore the original playback state.
- Verify user-facing native changes in the rendered Windows UI when practical. If live state prevents a check, report that behavior as unverified rather than simulating success.

## Change control

- Do not commit, push, merge, publish, install autostart, replace the running legacy application, or create an installer unless the user explicitly approves that action.
- Keep generated artifacts, secrets, machine-specific paths, and personal defaults out of commits.

## Native release signing gate

- Do not publish or label a native Windows artifact as release-ready while the app, installer, or generated uninstaller is unsigned. A checksum is not a publisher signature.
- Before a native release, verify Authenticode signatures after packaging and installation, then verify install, launch, compact/hover behavior, Start menu, optional startup, upgrade, and uninstall on Windows 11 with Smart App Control enabled.
- Keep unsigned CI artifacts explicitly labeled `unsigned`; they are development inputs only and must never be attached to a public GitHub Release.
- SignPath Foundation is the intended open-source signing route, but do not claim acceptance or signed status until the external approval and a complete working signing path are verified. Do not store or print signing credentials.
- The Inno Setup release path is incomplete until the signing provider confirms how the embedded app and generated uninstaller are signed. If that cannot be done, explain and obtain approval before changing installer technology.
